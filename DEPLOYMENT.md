# Тестовое размещение GainLab

## Рекомендуемая платформа

Для текущей архитектуры рекомендуется **Netlify Free**. Проект использует полноценный Next.js с App Router, серверным получением спортивных новостей, кешированием, `next/image`, Cache Components и Partial Prerendering. Netlify поддерживает эти возможности через свой адаптер Next.js без перевода приложения в статический экспорт.

**Cloudflare Pages** сейчас подходит только для статического экспорта Next.js. Такой переход потребовал бы менять архитектуру и лишил бы текущий сайт серверного новостного дайджеста. Если в будущем будет выбран Cloudflare, для этой архитектуры следует рассматривать **Cloudflare Workers с Vinext**, а не Pages, и отдельно проверить совместимость перед миграцией.

## Что уже подготовлено

- `netlify.toml` фиксирует production-сборку `pnpm build`, Node.js 22 и защиту от несовпадения версий клиентских ресурсов между публикациями.
- `packageManager` фиксирует pnpm 11.25.0; Netlify определит pnpm по `pnpm-lock.yaml` и установит указанную версию через Corepack.
- `postinstall` генерирует Prisma Client при чистой установке зависимостей. Сгенерированные файлы по-прежнему не хранятся в Git.
- `engines.node` документирует минимальную версию Node.js 20.9, требуемую установленной версией Next.js.
- Производственная сборка не зависит от запущенного локального Docker-контейнера: текущая витрина использует `lib/demo-data.ts`.

## Что потребуется перед первой публикацией

Папка `D:\ДОМ\Gainlab` на момент подготовки не является Git-репозиторием. Поэтому сначала потребуется инициализировать Git, проверить состав файлов первого коммита и только затем разместить репозиторий в GitHub, GitLab или Bitbucket. Секреты и локальный файл `.env` не добавлять в Git.

1. Инициализировать Git и создать проверенный первый коммит без секретов и локальных сборочных файлов.
2. Разместить репозиторий в GitHub, GitLab или Bitbucket.
3. Создать в Netlify новый проект через импорт репозитория.
4. Оставить корневую папку репозитория как Base directory. Команда сборки уже задана в `netlify.toml`; вручную добавлять `@netlify/plugin-nextjs` или указывать каталог публикации не нужно.
5. Запустить сначала Deploy Preview и проверить главную страницу, каталог, подменю, поиск, новости, мобильную версию и внешние ссылки.
6. После появления постоянного HTTPS-адреса при необходимости задать `NEXT_PUBLIC_SITE_URL` в настройках Netlify. Текущий код эту переменную пока не использует, поэтому для тестового запуска она не обязательна.

Для нынешней демоверсии `DATABASE_URL` на Netlify **не требуется**: PostgreSQL ещё не подключён к пользовательскому интерфейсу. Не следует переносить на хостинг локальную строку подключения из `.env.example`.

## Когда каталог будет подключён к базе

Перед публикацией версии с PostgreSQL понадобится:

1. создать управляемую PostgreSQL-базу, доступную из интернета;
2. сохранить production-значение `DATABASE_URL` только в переменных окружения хостинга;
3. применить миграции к production-базе отдельной контролируемой командой;
4. не запускать seed без отдельного подтверждения, поскольку он содержит тестовые данные;
5. повторно проверить поведение серверных функций и лимиты подключений базы.

Локальный PostgreSQL из `docker-compose.yml` предназначен только для разработки и не разворачивается на Netlify.

## Локальная проверка перед публикацией

```powershell
pnpm install --frozen-lockfile
pnpm check
```

Успешный `pnpm check` подтверждает типы, ESLint, автоматические тесты и production-сборку. Он не заменяет проверку Deploy Preview и не проверяет ещё не подключённую production-базу.

## Ограничения бесплатного теста

На актуальном тарифе Netlify Free доступно 300 кредитов в месяц с жёстким лимитом. При исчерпании лимита проекты приостанавливаются до следующего расчётного периода; автоматических списаний на бесплатном тарифе нет. Этого достаточно для малопосещаемой тестовой версии, но не следует считать бесплатный тариф готовой производственной инфраструктурой.
